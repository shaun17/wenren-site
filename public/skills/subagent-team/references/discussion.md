# 协商

目标是帮助作出有依据的判断，保留重要分歧；不以一致、轮数或观点数量作为完成标准。

## 局限

所有参与者都是同一家模型，盲区可能相同。用不同立场（如支持方、红队、实现成本视角）拉开角度；用户点名模型时可混用 `model`。汇总时说明这一局限，不把"多方一致"当成独立验证。

## 独立首轮

1. 建 `.team/discussions/D-xx/`，写 `brief.md`：问题、目标、约束、已知事实、已做实验、需要何种答案。证据放 `evidence/`，保留原件或位置。主持人的偏好不写成结论；确有假设就标为假设。
2. 给每位参与者分配字母（A、B…）、立场（可选）和输出文件 `D-xx/<字母>.md`。参与者数量以覆盖问题为准；用户点名一位，就只开一位。
3. 在同一条消息里并行派发，`subagent_type: general-purpose`，不加 worktree。prompt：

   ```
   你是协商参与者 <字母>，立场：<立场或"独立判断">。读 <brief.md 绝对路径> 和 evidence/。
   只读，不修改仓库，不读同目录下其他参与者的文件。把发言写到 <输出文件绝对路径>，
   不超过 <长度，普通设计问题约 600～800 字>，使用以下三个标题：
   ## 立场   ## 理由   ## 什么会让我改变看法
   事实附原始出处，推断标清。最终回复只写一句立场和输出文件路径。
   ```

首轮互不读取依靠的是约定和同时派发，不是机械隔离。

## 主持人判断是否继续

核对首轮结果后，先判断哪些问题仍会改变决策：

- 依据足够、剩余不确定性不影响判断：直接汇总。
- 缺具体证据：安排一次明确取证；需要用户偏好或约束时问用户。
- 仍有实质分歧：只向相关参与者追问。用 SendMessage 发给其 agent ID，附关键原文位置，要求写到新文件 `D-xx/<字母>-2.md`。不让所有人重写整份意见。

允许参与者因新证据、更好的论证或约束澄清而改判，不强迫改判。注意相互引用的观点是否有独立依据，避免把循环赞同当证据。定向追问通常一次即可；继续讨论不能带来新信息时，列明缺口后结束。

## 红队

允许提出未证实的风险，但必须说明触发条件、影响和验证方法，区分事实、假设与个人判断。检查后也可以报告没有重大异议，此时列出检查过的项目，不为履行角色而制造反对意见。

## 汇总

主持人直接交付：建议与理由、重要分歧、尚缺证据、适用条件。只列实际可行的选项。简单问题给短结论；复杂决策附各方发言文件的路径。
把各方观点与主持人的判断分开，说明为什么采纳某项。用户已委托决策时直接给决定，否则保留需要用户取舍的部分。
